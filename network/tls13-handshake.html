핵심 차이 — 아래 두 버튼을 비교해 보세요
TLS 1.2 RSA: 브라우저가 비밀(pre-master)을 서버 공개키로 잠가서 선 위로 보낸다 → 도청자 녹화본에 그 잠긴 비밀이 남는다 → 2년 뒤 개인키를 훔치면 열린다.
TLS 1.3 ECDHE: 양쪽이 공개값(key_share)만 교환하고 비밀은 각자 계산 → 선 위로 비밀이 한 번도 지나가지 않는다 → 개인키를 훔쳐도 과거는 안전. 개인키는 서명(CertificateVerify)에만 쓴다.

3단계 정리 (TLS 1.3)

#누가무엇을왜암호 방식
①브라우저ClientHello — random, 지원 버전·암호 스위트, key_share(임시 DH 공개값), SNI, ALPNkey_share를 처음부터 보내서 왕복 1번(1-RTT). SNI로 어느 인증서를 줄지 알림평문 key_share = 비대칭 계열 공개값
②서버ServerHello — random, 고른 스위트, 자기 key_share공개값이 모였으니 양쪽이 각자 같은 공유 비밀 계산(ECDHE). 비밀은 전송 안 됨평문 key_share = 비대칭 계열 공개값
—양쪽공유 비밀 → 핸드셰이크 키이후는 인증서까지 전부 암호화ECDHE(비대칭 계열)로 → 대칭키를 만들어 냄
③④서버{EncryptedExtensions} {Certificate} 서버 인증서 + 중간 CA 인증서(사본)"이 공개키는 api.example.com의 것" — CA 보증서. 중간 CA 인증서는 발급받을 때 CA에게서 같이 받은 공개 문서라 서버가 대신 전달 (중간 CA의 개인키는 서버에 없음)대칭키 암호화 (server 핸드셰이크 키 · AES-GCM)
⑤서버{CertificateVerify} 대화 전체에 개인키로 서명인증서는 누구나 복사 가능. 개인키 소유를 증명 → 중간자 차단운반: 대칭키 암호화 내용: 비대칭 서명 (서버 개인키)
⑥서버{Finished} 대화 전체의 MAC①②가 바꿔치기(다운그레이드)되지 않았음을 확인운반: 대칭키 암호화 내용: MAC (대칭 · HMAC)
⑦브라우저검증: 서버 인증서 → 중간 CA 인증서 → 루트 CA까지 체인 · 도메인(SAN) · 유효기간·폐기 · CertificateVerify · Finished하나라도 실패하면 중단체인·⑤ 서명 확인: 공개키 (비대칭) ⑥ 확인: MAC (대칭)
⑧브라우저{Finished}브라우저 쪽 대화도 같다는 확인대칭키 암호화 (client 핸드셰이크 키)
⑨브라우저[GET /orders] 애플리케이션 키 + AEAD이후 데이터는 빠른 대칭 암호 + 변조 검출대칭키 암호화 (애플리케이션 키 · AES-GCM)

4대칭키 vs 비대칭키 — 어디에 무엇을 쓰나

🗝 비대칭 (공개키 · 개인키)🔐 대칭 (같은 키로 잠그고 엶)
TLS 1.3에서 쓰는 곳① ECDHE 키 합의 — 공개값 aG·bG만 교환해 같은 비밀을 각자 계산
② CertificateVerify 서명 — 서버 개인키로 서명, 인증서 공개키로 확인
③ 인증서 체인 검증 — CA 서명을 CA 공개키로 확인		③④⑤⑥⑧ 핸드셰이크 메시지 암호화 (핸드셰이크 키)
⑨ 이후 모든 HTTP 데이터 암호화 (애플리케이션 키)
Finished의 MAC
데이터를 "암호화"하나?아니오. TLS 1.3에서 비대칭으로 데이터를 잠그는 일은 없다예. 실제 데이터는 전부 대칭키(AES-GCM 등)로
왜 그렇게 나누나느리고 한 번에 작은 데이터만 다룰 수 있음 → 키 합의와 신원 증명에만수백~수천 배 빠름(CPU에 AES 전용 명령어) · 크기 제한 없음 → 실제 데이터에
TLS 1.2 RSA (비교)pre-master secret을 서버 공개키로 "암호화" — 비대칭으로 잠근 유일한 데이터. 그래서 개인키가 털리면 과거가 열림세션 키로 데이터 암호화 (1.3과 같음)
⚠ 흔한 오해: "HTTPS는 공개키로 데이터를 암호화한다" → 아니다. 공개키 계열은 키 합의(ECDHE)와 서명에만 쓰고, 데이터는 그렇게 만든 대칭키로 암호화한다.
면접용: "브라우저가 ClientHello에 지원 스위트와 임시 DH 공개값(key_share)을 담아 보내고, 서버가 ServerHello로 자기 key_share를 보내면 양쪽이 ECDHE로 같은 공유 비밀을 각자 계산합니다. 이후 암호화된 채로 서버가 인증서 체인, 개인키로 대화 전체에 서명한 CertificateVerify, Finished를 보내고, 브라우저는 루트 CA까지 체인과 도메인·유효기간·서명·Finished를 검증한 뒤 자신의 Finished를 보냅니다. 왕복은 1번이고, 임시 키를 버리므로 나중에 개인키가 털려도 과거 대화는 안전합니다."

근거: RFC 8446 — TLS 1.3 (Figure 1 "Message Flow for Full TLS Handshake" · "CertificateVerify: A signature over the entire handshake using the private key corresponding to the public key in the Certificate message." · "Static RSA and Diffie-Hellman cipher suites have been removed; all public-key based key exchange mechanisms now provide forward secrecy.")

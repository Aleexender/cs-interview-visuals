트랜잭션 · undo log · MVCC

2026-10-12 모의면접에서 다룬 내용을 그림으로 정리했습니다. MySQL InnoDB와 Spring @Transactional 기준입니다.

0출발점: ③에서 예외가 나면 DB에는 무엇이 남나?

@Transactional
fun order(userId: Long, productId: Long) {
    stockRepository.decrease(productId)   // ① UPDATE
    orderRepository.save(Order(...))      // ② INSERT
    pointService.use(userId, 1000)        // ③ 예외!
}
답: 아무것도 남지 않습니다. 이걸 보장하는 성질은 ACID 중 Atomicity(원자성)입니다. 전부 반영되거나 전부 반영되지 않아요.
그런데 "원자성 때문"은 이름일 뿐입니다. 실제로 누가 무엇을 하는지를 아래에서 차례로 봅니다.

1스프링 쪽: "트랜잭션 시작" = auto-commit 끄기

프록시.order() 호출됨
① 커넥션 풀에서 커넥션 1개 획득
② connection.setAutoCommit(false)  ← 이게 "트랜잭션 시작"
③ 진짜 order() 호출
UPDATE stock …  (실행됐지만 아직 커밋 안 됨)
INSERT orders …  (실행됐지만 아직 커밋 안 됨)
pointService.use() → 예외!
④ 예외 감지 → connection.rollback()  (정상이었다면 commit())
⑤ auto-commit 원래대로 복구 → 커넥션 풀에 반납
auto-commit을 껐을 때 (@Transactional)
①②③이 트랜잭션 하나로 묶임
③ 예외 → rollback → ①② 모두 취소
auto-commit 그대로 (기본값)
SQL 한 문장마다 즉시 커밋
③ 예외 → 재고 줄고 주문은 생겼는데 포인트는 그대로

2DB 쪽: rollback은 어떻게 원래 값을 아나? → undo log

1. 먼저 기록행을 고치기 직전에 바뀌기 전 값(qty=10)을 undo log에 적는다
2. 그다음 수정행의 값을 qty=9로 바꾼다
3. 롤백하면undo 기록을 역순으로 적용한다. ② INSERT 취소 → ① 값 10으로 복구
순서가 반대면(수정하고 나서 기록) 그 사이에 장애가 났을 때 원래 값을 잃어버립니다. 그래서 "먼저 기록, 나중에 수정"입니다.

3행 안의 숨은 컬럼 두 개 + undo log = 버전 체인

각 행에는 숨은 컬럼이 두 개 있습니다. undo log 자체가 아니라, undo log를 가리키는 정보예요.

이름위치내용
DB_TRX_ID행 안이 버전을 만든 트랜잭션 번호, 즉 도장
DB_ROLL_PTR행 안이전 버전이 있는 undo 레코드를 가리키는 포인터
undo log행 밖이전 버전의 값
테이블의 행 (최신)
qty = 8
도장 103
ROLL_PTR
──►
undo log (한 칸 과거)
qty = 9
도장 100
ROLL_PTR
──►
undo log (두 칸 과거)
qty = 10
도장 90
테이블에는 최신 값 하나만 있습니다. 옛날 값들은 undo log에 Ctrl+Z 이력처럼 줄줄이 연결돼 있어요.
값 8에는 "커밋됨" 표시가 없습니다. 있는 건 누가 썼는지(도장)뿐이에요.

4Read View(사진): 값이 아니라 "작업 중인 사람 명단"

B가 첫 일반 SELECT를 하는 순간 찍는 사진입니다. 데이터를 복사하지 않습니다. 어떤 버전을 고를지 정하는 기준표예요.

📸 B의 Read View
명단(사진 순간 커밋 안 한 번호) : [100, 103]
가장 작은 명단 번호            : 100
다음 발급 번호                   : 105  (이 이상은 사진 뒤에 온 사람)

번호표를 눌러 보세요. B가 그 도장이 찍힌 버전을 볼 수 있는지 판정합니다. 점선 테두리는 명단에 있는 번호예요.

① ~99 : 사진 전에 다 끝남
② 100~104 : 섞여 있음 → 명단 확인
③ 105~ : 사진 뒤에 옴
번호를 선택하면 여기에 판정 과정이 나옵니다.

5B가 SELECT 할 때 판정하는 순서

0행의 최신 버전을 꺼내 도장을 본다
a도장이 내 번호인가? (내가 고친 것)보임
b도장 < 가장 작은 명단 번호(100)인가? → ①보임
c도장 ≥ 다음 발급 번호(105)인가? → ③안 보임
d그 사이(②)면 명단에 있나?있음 → 안 보임 없음 → 보임
↺안 보이면 ROLL_PTR을 따라 한 칸 과거 버전을 만들어 a부터 다시. 체인 끝까지 없으면 그 행은 B에게 존재하지 않음
이 과정에 락 확인은 한 번도 없습니다. 그래서 일반 SELECT는 쓰는 트랜잭션을 기다리지 않아요(consistent nonlocking read).
"복원"은 B만 보는 복사본입니다. 실제 행은 그대로 8이에요.

"보인다" = 그 버전의 값이 B의 SELECT 결과로 나온다는 뜻입니다.

상대가 한 일"안 보인다"면 B의 결과는
UPDATE바뀌기 전 값이 나온다
INSERT그 행이 결과에 아예 없다
DELETE지워진 행이 아직 나온다

6가장 헷갈린 지점: "지금 커밋됐나"는 판정에 쓰이지 않는다

오늘 세 번 흔들린 곳입니다. 기준은 언제나 사진 찍은 순간이에요.

📸 B 사진
102 시작커밋
103 (사진 때 작업 중) 시작"방금" 커밋
D = 106 시작커밋
번호시작커밋구간B에게근거
102사진 전사진 전②보임명단에 없음
103사진 전사진 후②안 보임명단에 있음. 지금 커밋됐어도 사진은 그대로
106사진 후사진 후③안 보임번호 ≥ 105. "미래"는 이 경우만 가리킴
"이미 커밋했으니 과거" ❌ → 오늘 D(106)와 103에서 두 번 이렇게 판정했습니다.
정확한 규칙: "사진을 찍은 시점 이전에 커밋된 버전과 내가 바꾼 버전만 보인다."

7왜 행에 "커밋됨" 표시를 안 붙이고 사진을 따로 둘까?

같은 버전이라도 읽는 사람마다 답이 다르기 때문입니다.

📸 C 사진
103 커밋
📸 E 사진
C (103 커밋 전 사진)
103이 쓴 qty=8 → 안 보임 → 옛날 값
E (103 커밋 후 사진)
103이 쓴 qty=8 → 보임 → 8
그래서 역할을 나눕니다. 행은 누가 썼는지(번호)만 기록하고, 읽는 사람은 각자 사진을 갖고, 둘을 대조합니다. 명단에 번호가 들어 있는 이유도 행에 찍힌 게 번호라서예요.
이게 Multi-Version Concurrency Control이라는 이름의 뜻입니다.

사진을 고정하면 얻는 것: 일관성

B: 잔액 합계 리포트사진 고정 (RR)매번 새로 커밋된 걸 봄
X 읽음10001000
← 103: X −100, Y +100 커밋
Y 읽음500 (이체 전)600 (이체 후)
합계1500 ✅1600 ❌ 100원 생김

8REPEATABLE READ vs READ COMMITTED = 사진을 언제 찍나

격리 수준사진을 찍는 시점A가 커밋한 뒤 다시 읽으면
REPEATABLE READ (MySQL 기본)트랜잭션의 첫 일반 읽기에서 한 번계속 10 → 반복 읽기 보장, 새 INSERT 행도 안 보임
READ COMMITTED매 SELECT마다 새로9가 보임 → non-repeatable read
dirty read는 RR이라서가 아니라 READ COMMITTED부터 막힙니다.
긴 트랜잭션이 위험한 이유: 오래된 사진이 옛 버전을 필요로 하니 undo log를 지우지 못하고 계속 쌓입니다.

9면접용 문장 (평서형으로 끊기)

  1. @Transactional의 트랜잭션 시작은 커넥션의 auto-commit을 끄는 것이고, 끝날 때 결과에 따라 commit 또는 rollback을 호출하는 것입니다.
  2. 원자성은 undo log로 보장됩니다. 행을 바꾸기 전에 이전 값을 기록해 두고, 롤백 시 역순으로 되돌립니다.
  3. 일반 SELECT는 락 없이 Read View 기준으로 보이는 버전을 고르고, 보이지 않으면 undo log 체인을 따라 이전 버전을 만들어 읽습니다.
  4. 일반 SELECT는 스냅샷 시점 이전에 커밋된 버전과 자기 자신이 바꾼 버전만 봅니다.

생성자 주입 vs 필드 주입 — 3D로 "언제 넣느냐" 보기

2026-10-26 모의면접 Q1-9 · 앞줄(초록 이름표) = 생성자 주입, 뒷줄(주황 이름표) = 필드 주입. 두 줄이 똑같은 조립 라인을 나란히 지나갑니다.

1질문 · 내 답 · 판정

내 답변 (원문)
"autowired 로 하면 self invocation 문제가 발생할수도 있어서 생성자 주입을 권장함."
❌ 오답 (깊이 0). 주입 방식과 self-invocation은 관계가 없다. self-invocation은 this로 호출해 프록시를 우회하는 호출 경로 문제라 어떤 주입 방식에서도 똑같이 생긴다. 오늘 배운 용어를 인과 없이 결론에 붙인 경우.
정답의 뿌리 — 딱 한 가지
"의존성을 언제 넣느냐"
· 생성자 주입: ① 생성자 호출 때 들고 태어난다
· 필드 주입: ①에서 빈 채로(null) 태어나고 ② 필드 주입에서 컨테이너가 리플렉션으로 채워 넣는다
→ 이 차이 하나에서 final · 불완전 객체 · 테스트 · 순환 참조 네 가지 이유가 전부 나온다.
// 생성자 주입 (Kotlin 주 생성자 + val)
class OrderController(private val orderService: OrderService)

// 필드 주입
class OrderController {
    @Autowired lateinit var orderService: OrderService
}

23D 조립 라인 — 버튼마다 이유 하나씩

OrderController 객체   의존성 (@2 OrderService)
빈 칸 = null   🔒 = final (다시 대입 불가)
🖱 드래그해서 돌려 보기 · 더블클릭 = 원위치

3정리

이유생성자 주입필드 주입①/② 근거
1. final (불변)✅ val / final 가능 → 바꿔치기 시 컴파일 에러❌ lateinit var → 나중에 누가 바꿔도 조용히 성공①에서 한 번 대입 vs ②에서 리플렉션으로 사후 대입
2. 불완전한 객체✅ ①이 끝나면 이미 완전❌ ①~② 사이 의존성 null → 생성자에서 쓰면 NPE②가 ① 뒤에 일어나기 때문
3. 테스트✅ OrderController(mock)으로 바로 생성❌ new로 만들면 ②를 해 줄 컨테이너가 없어 영원히 null②는 컨테이너만 할 수 있다
4. 순환 참조✅ A↔B면 기동 실패로 바로 드러남⚠️ ①을 빈 채로 넘기고 ②에서 서로 채워 문제를 숨김 (Boot 2.6+는 기본 금지)①에 상대가 필요하냐 아니냐
5. 의존성 개수파라미터가 늘면 바로 보임 (책임 과다 신호)필드가 늘어도 티가 잘 안 남—
면접용: "생성자 주입은 객체가 생성되는 순간 의존성이 모두 채워지기 때문에 필드를 final로 둘 수 있고, 의존성이 null인 불완전한 상태가 존재하지 않습니다. 그래서 스프링 없이 new로 테스트할 수 있고, 순환 참조도 기동 시점에 바로 드러납니다."

@Transactional 안에서 runAsync로 스레드가 바뀌면

③만 다른 스레드(worker-3)에서 돌면 사물함(ThreadLocal)도, 호출 스택도 따로입니다. 그래서 worker-3은 트랜잭션 커넥션을 못 찾고, worker-3의 예외는 프록시에 닿지 않아 ①②는 커밋됩니다.
@Transactional
fun order(userId: Long, productId: Long) {
    stockRepository.decrease(productId)          // ① exec-7
    orderRepository.save(Order(...))             // ② exec-7
    CompletableFuture.runAsync {                 // ③ worker-3
        pointRepository.use(userId, 1000)        //    → 여기서 예외 발생!
    }.join()                                      // ← 결과를 기다림
}                                                // ← exec-7은 이 줄에 도착

순서는 항상 같나?아니다worker-3이 언제 실행될지는 스케줄러 마음. exec-7이 커밋할 때 worker-3은 시작 전일 수도, 끝났을 수도 있음
.join()을 붙이면 exec-7이 기다렸다가 예외를 CompletionException으로 감싸 exec-7 스택에서 다시 던집니다. 그러면 프록시가 받아서 ①②를 rollback해요.
단, ③은 여전히 다른 커넥션(conn#45)이라 같은 트랜잭션이 아닙니다. ③이 무언가를 커밋한 뒤에 실패했다면 그건 rollback되지 않아요. 같은 트랜잭션이어야 하는 작업은 애초에 같은 스레드에서 해야 합니다.
면접용: "스프링 트랜잭션은 ThreadLocal에 묶여 있어서 다른 스레드로 넘어가면 전파되지 않습니다. 새 스레드는 트랜잭션 밖에서 별도 커넥션으로 실행되고, 거기서 난 예외도 원래 스레드의 프록시에 도달하지 않아 원래 트랜잭션은 커밋됩니다."

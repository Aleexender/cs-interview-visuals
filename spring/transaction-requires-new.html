REQUIRES_NEW: 예외 전파 vs 트랜잭션 전파 · 커넥션 2개 · 풀 데드락

@Service
class PointService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    fun use(userId: Long, amount: Int) { throw PointNotEnoughException() }   // RuntimeException
}

@Service
class OrderService(...) {
    @Transactional
    fun order(userId: Long, productId: Long) {
        stockRepository.decrease(productId)          // ①
        orderRepository.save(Order(...))             // ②
        try { pointService.use(userId, 1000) }       // ③
        catch (e: PointNotEnoughException) { log.warn("포인트 부족") }
    }
}

2"Propagation"은 예외가 아니라 트랜잭션의 전파

예외 전파 (exception)

층: JVM 호출 스택
예외가 호출한 쪽으로 위로 올라가는 것. throw → 위 프레임 → … → 누가 catch하면 멈춤.
전파 속성과 무관하게 항상 일어납니다. REQUIRES_NEW여도 use()의 예외는 order()까지 올라와요. 그래서 order()의 catch가 잡을 수 있는 거고요.

트랜잭션 전파 (Propagation)

층: 스프링 트랜잭션 · DB 커넥션
이미 트랜잭션이 있을 때 안쪽 @Transactional이 그걸 이어 쓸지, 새로 만들지.
REQUIRED = 이어 씀(물리 1개) · REQUIRES_NEW = 새로 만듦(물리 2개).
예외가 어디로 가는지는 바꾸지 않습니다. 예외가 났을 때 무엇이 롤백되는지를 바꿔요.
이번 답의 오류는 두 "전파"를 섞은 것 = 층 혼동. "Propagation"이 보이면 "트랜잭션이 어떻게 이어지나"로 읽으세요.

4풀 데드락 시뮬레이터 — 요청마다 커넥션 2개가 필요하면

모든 요청이 동시에 order()에 들어온 최악의 경우. 각 요청은 ① 바깥 커넥션 1개를 쥔 채 ② REQUIRES_NEW용 1개를 더 받아야 끝납니다.
커넥션 풀
실제 장애 모습: 평소엔 멀쩡하다가 피크 때만 모든 요청이 HikariCP connectionTimeout(기본 30초) 동안 멈췄다가
SQLTransientConnectionException: Connection is not available, request timed out after 30000ms 로 한꺼번에 실패합니다.
대응내용
풀 크기 공식풀 ≥ Tn × (Cm − 1) + 1 (Tn = 동시 스레드 수, Cm = 한 스레드가 동시에 쥐는 최대 커넥션 수)
구조 변경바깥이 커밋된 뒤 처리: @TransactionalEventListener(phase = AFTER_COMMIT) 등
남발 금지REQUIRES_NEW는 감사 로그처럼 꼭 독립적으로 남아야 하는 것에만
면접용: "REQUIRES_NEW는 바깥 트랜잭션을 일시 중단하고 새 커넥션으로 독립 트랜잭션을 열기 때문에 안쪽 롤백이 바깥에 영향을 주지 않습니다. 대신 한 요청이 커넥션을 두 개 쥐게 되어, 동시 요청이 풀 크기에 닿으면 서로 커넥션을 기다리는 풀 데드락이 생길 수 있습니다."
